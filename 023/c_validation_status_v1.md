# c_validation_status — kv_bug_023

- **bug_id:** kv_bug_023
- **module:** keyvault
- **status:** no_witness

## Conclusion

No software-visible witness exists for the claim, and none is expected: the case
resolved to `false_alarm`, so there is no software-observable violation to
demonstrate.

The software-side observation here inverts the claim rather than supporting it.
The lock setting the candidate says hardware must perform is already reachable
from software for every entry, and the tree exposes the register bits to firmware
directly. `src/integration/rtl/caliptra_reg/caliptra_reg.h:1940-1947` gives
`CLP_KV_REG_KEY_CTRL_0` fields `LOCK_WR`, `LOCK_USE` and `CLEAR` at bits 0, 1 and
2. A single write of bit 1 by an earlier boot stage makes hardware suppress the
read for every client at `src/keyvault/rtl/kv.sv:234` and raise `kv_rd_resp.error`
at `:240`, and the same write makes the bit sticky through the `swwel` feedback at
`src/keyvault/rtl/kv.sv:188`, so no later stage can undo it by writing the
register.

A C test that provisioned an entry, advanced a stage and observed the entry still
usable would be demonstrating firmware declining to write `LOCK_USE`, not hardware
failing to enforce a property. The register-level behavior that would matter for
such a test is already measured directly at the module boundary in
`proof/tb/kv_lock_enforcement_tb.sv`, through real AHB writes and reads to
`KEY_CTRL` rather than through forced internal state, so a C wrapper would add a
software layer over an observation that is already software-shaped.

## Rationale

For a `false_alarm` the useful software-observability statement is whether the
security duty the candidate assigns to hardware is discharged elsewhere and
visibly so. Here it is: the duty sits with firmware per
`src/keyvault/config/keyvault.md:225`, the register bits exist and are exported to
firmware, and hardware enforces them once written, including against the writer's
successors. There is nothing for a C test to assert that these paths do not state
directly.

One open question in this case would need a different kind of test than a C
witness, and is recorded rather than attempted: `src/keyvault/rtl/kv.sv:176-177`
makes both lock terms inert while `fw_update_rst_window` is asserted. That window
is generated by the boot FSM at `src/soc_ifc/rtl/soc_ifc_boot_fsm.sv:90` and is
not software-controllable, and `src/integration/rtl/caliptra_top.sv:828` gates the
microcontroller clock during it, so firmware cannot execute inside the window to
observe it. Settling that behavior requires a top-level simulation that asserts a
firmware-update reset while a crypto engine read is in flight, not a C test.
