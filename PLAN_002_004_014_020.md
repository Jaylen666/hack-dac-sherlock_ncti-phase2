# Plan: BUG-002, BUG-004, BUG-014, BUG-020

Four cases, run one at a time. Each case goes through the convergence skill to
produce the proof artifacts, then through the packager skill to produce the
uploadable attachment. The packager step is new relative to the previous batches
in this directory, which stopped at the four metadata files.

## Per-case pipeline

Stage A — convergence (`caliptra-bug-proof-convergence`)

1. Read the cited RTL and its consumers. Establish the expected behaviour from
   the audited tree's own RDL, in-tree docs, or an adjacent correct case in the
   same file. Never from a second implementation.
2. Frame the security claim in the `attacker / input / precondition /
   protected_asset / property / implemented_logic` slots. If a slot cannot be
   filled, the case is `hold`, not a bug.
3. Write `proof_plan_v1.json` including a `non_findings` pre-commitment.
4. Build the witness: `proof/tb/<mod>_bug_<id>_tb.sv`, `proof/scripts/run_bug_<id>_sim.sh`,
   `proof/scripts/run_bug_<id>_proof.sh` (structural audit),
   `proof/scripts/run_bug_<id>_negative_control.sh`.
5. Run all three. Structural audit must reach `structural_gates_passed=N/N` and
   `result=PASS`. Sim must reach `PROOF_RESULT: PASS`. Negative control must
   reach `NEGATIVE_CONTROL: PASS`.
6. Self-attack the proof: check for vacuity, check the baseline actually moves,
   check the discriminator separates the claimed cause from the obvious
   alternative.
7. Write `proof_result_v1.json`, `submission_v1.json`, `c_validation_status_v1.md`.
   Score CVSS with the script, never by hand.
8. Re-run the witness sim last, so the submitted `run.log` and `witness.log`
   describe the unmodified tree rather than the negative control's patched copy.
9. Validator must pass with 0 failures. Provenance gate must show no
   `comparison-rtl`, `source-diff`, or `known-answer` hits.
10. Delete any VCS build tree; keep the logs.

Stage B — packaging (`bug-submission-packager`)

11. Normalize `bug_id` to the zero-padded three-digit contest id, preserving the
    repo-style name in `bug_name`. Audit `adversary_profile` against the four
    handbook categories.
12. Add the attachment note inside `location_or_code_reference` for cases that
    ship a real witness; omit it for a pure static-audit case.
13. Build `submission_record/<bug_id>/` with `scripts/`, `tb/`, `logs/`,
    `README.md`, `manifest.json`. Copy by direct review, not by script. Never
    copy `submission*.json`, `proof_result*.json`, or `proof_plan*.json`.
14. Rewrite absolute paths in the packaged script copies to package-local paths.
15. Run the provenance gate over the whole numbered case and confirm no packaged
    file carries a workstation path or a prohibited term.

## Case notes

### BUG-002 — aes, KV operation no longer masks register output

- Site: `src/aes/rtl/aes.sv:197`, inside the `kv_data_intercept_reg` flop at
  lines 188-203. `hw2reg_data_out_mask_en <= ~caliptra2aes.block_reg_output;`
  drops the `~kv_en` term, so the mask is released during a KeyVault operation.
- Expected behaviour source: `src/aes/config/aes.md:35-37` requires the AES-ECB
  decrypt result routed to a KeyVault destination to be withheld from the
  plaintext `dataout` register API. The reset and completion branches of the same
  flop both drive the mask to `1'b1`, which shows the safe default is `masked`.
- Witness shape: `directed_sim` on one `aes` instance. Accept the first input
  word with `kv_en=1` and `block_reg_output=0`, then observe
  `hw2reg_data_out_mask_en`. Control: the same sequence with `kv_en=0`, which
  must produce the same mask value the defect produces, since that is the case
  the surviving term was written for. Discriminator: `block_reg_output=1` with
  `kv_en=1`, which must mask regardless, separating "the mask never works" from
  "the `kv_en` term is missing".
- Highest-value observation if reachable: whether `data_out` readback actually
  returns cipher material. That decides confidentiality versus defence-in-depth.
- Negative control: restore the conjunction at line 197.
- Risk: `aes` is a large OpenTitan-derived block. Check the filelist elaborates
  before investing in the testbench. If the unit build is impractical, fall back
  to `structural_audit` plus a compile witness and record the boundary.

### BUG-004 — aes_reg_top, key share registers readable by software

- Site: `src/aes/rtl/aes_reg_top.sv:1728-1765`. The sixteen readback cases for
  `key_share0[0:7]` and `key_share1[0:7]` return `reg2hw.key_share*.q` instead of
  constant zero.
- Expected behaviour source: strongest available, and it is in the same case
  statement. `addr_hit[0]` at lines 1730-1733 drives `reg_rdata_next` bits to
  `'0` explicitly, so write-only-with-zero-readback is this file's own idiom. The
  RDL for these registers should confirm the software access policy; read it
  before writing the claim.
- Witness shape: `directed_sim` on one `aes_reg_top`. Write a known pattern to
  each key share word over the register bus, read it back, and assert zero. This
  is the cleanest witness of the four: the observation is a bus read and the
  asset is the key share itself.
- Control: read a register that is legitimately readable, to show the read path
  works and the zero is not a dead bus. Containment: no bus error.
- Negative control: force the sixteen cases to constant zero.
- Expected severity: this is the only one of the four with a direct
  confidentiality claim, so it should carry the highest CVSS. Key shares are the
  masked representation of the key; recovering both shares recovers the key. State
  in the claim whether both shares are readable, since that is what makes it a
  key recovery rather than a partial leak.

### BUG-014 — hmac, final-block LAST protocol removed end to end

- Sites: `src/hmac/rtl/hmac_core.sv:24-44` has no `last_cmd` port;
  `src/hmac/rtl/hmac.sv:245-260` has no LAST control and
  `src/hmac/rtl/hmac.sv:424-429` ties `error2_sts.hwset` to `1'b0` with a TODO;
  `src/hmac/rtl/hmac_reg.sv:868-888` marks bit 5 Reserved;
  `src/hmac_drbg/rtl/hmac_drbg.sv:125-158,225-255` has no `HMAC_last`.
- Expected behaviour source: `docs/CaliptraHardwareSpecification.md:1129,1134`
  requires the last block to carry padding and length and to chain from the
  previous block's result.
- Witness shape: this is a removal spanning four files, so the structural audit
  carries most of the weight: the absence of the port, the Reserved bit, the tied
  interrupt. Pair it with a `directed_sim` that shows the software-visible
  consequence. Two candidates, pick by what elaborates:
  (a) write CTRL bit 5 and read it back to show it does not stick, proving the
      control the spec requires is unreachable to software;
  (b) drive a LAST-alone command and show no error is reported, since
      `error2_sts` is the register that should flag it and it is tied low.
  Option (b) is the stronger security claim: an illegal command is silently
  accepted rather than rejected.
- Negative control: harder here, because the fix spans four files and adding a
  port changes an interface. Prefer a control targeted at whatever the sim
  actually observes — for (b), un-tie `error2_sts.hwset` and drive it from a
  locally derived LAST-alone condition, labelled an independently constructed
  remediation control.
- Risk: the honest status is likely `partial_proof`. A missing finalization
  protocol means the digest is computed over unpadded data, but demonstrating a
  forgery needs a KAT the audited tree does not carry. Claim the reachable part:
  software cannot request finalization and is not told its command was illegal.

### BUG-020 — boot_flow_monitor deleted

- The module file does not exist in the audited tree. Confirmed absent.
- Anchors: `src/integration/rtl/caliptra_top.sv:510-535`, where debug gating
  enters the CPU instance with no monitor between them, and
  `src/integration/rtl/caliptra_top.sv:1185-1210`, where the KV instance has no
  boot-flow ports.
- Expected behaviour source: `src/keyvault/config/keyvault.md:223-225,249-253`
  describes the boot-flow transition events the KeyVault policy consumes.
- Witness shape: `structural_audit` is the proof here, since there is no module
  to instantiate and no signal to drive. Gates must establish, positively and
  negatively: the in-tree specification names the transition events; no file in
  the tree declares or instantiates a boot-flow transition detector; the KV
  instance's port list has no boot-flow inputs; the ICCM region configuration
  that the detector would have consumed does exist, so the inputs are present
  and only the consumer is missing.
- Per the packager skill, a pure static-audit case gets an empty `tb/`, no
  manufactured testbench, and no attachment note claiming exploit code. Compile
  the cited RTL as baseline evidence that the anchor paths are live, and say in
  the README why no same-platform dynamic witness exists.
- Expected status: `partial_proof`. A deleted detector is a real gap, but the
  downstream policy consumers are separately numbered, so this case should claim
  the missing event source and not the policy failures.

## Ordering

BUG-004 first: cleanest witness, direct confidentiality claim, and it establishes
the `aes_reg_top` build for BUG-002 to reuse if that build turns out to be the
practical boundary. Then BUG-002, same block. Then BUG-014, which is the largest

the audit's completeness.

## Standing constraints

- Reference-blind: one DUT, one checkout, port-driven only. No `force`, no
  deposit, no hierarchical assignment, no second tree.
- Marker convention: the testbench prints `result=PASS` only on success. The
  failure branch prints `PROOF_RESULT: FAIL` with no `result=` line, because the
  negative control is supposed to reach it and a bare `result=FAIL` would be read
  as a real failure by the log scanners.
- Sim scripts grep `TBFAIL global timeout`, not bare `TBFAIL`.
- Absolute-path provenance findings are accepted and left alone by standing
  decision; only `comparison-rtl`, `source-diff`, and `known-answer` classes are
  treated as blocking.
- Report honestly. Where the reachable claim is narrower than the candidate's
  stated impact, file `partial_proof` with an explicit `blocker` rather than
  inflating it.
